Executive decision

Repair identity and indexability before publishing more content

Current risk: every page points search engines to a different, non-resolving canonical domain and publishes structured data for an unrelated lawn-care business. These signals can prevent correct indexing and teach answer engines the wrong entity.

The site already has useful foundations: the homepage and six articles are statically rendered, primary content appears in HTML, headings are clear, and the FAQ provides direct answers. The recommended sequence is therefore recovery first, trust second, content expansion third, and continuous measurement thereafter.

Delivery roadmap

Four implementation phases

Phase 0P0 · 1–2 days

Restore truthful, indexable identity

  1. Confirm the preferred canonical origin, expected to be https://www.empoweredwithinna.com, and centralize it as a shared site configuration value.
  2. Redirect every HTTP/HTTPS and apex/www variant to the preferred host in one hop.
  3. Remove the unrelated lawn-care JSON-LD immediately. Add only owner-verified Organization, WebSite, and—when verified—Person data with stable IDs.
  4. Create Next.js app/robots.ts and app/sitemap.ts; remove the empty singular app/robot.ts.
  5. Move page metadata to the App Router Metadata API. Create a typed post registry used by article routes, the blog index, sitemap, and schema.
  6. Give every route a unique title, description, self-canonical, Open Graph URL/image, and accurate robots policy.
  7. Fix or remove all broken image, icon, and manifest references; remove placeholder site-verification values.
  8. Remove the duplicated homepage header/main and add automated production SEO smoke tests.
Phase 1P1 · 3–7 days

Establish trust and editorial controls

  1. Run an owner fact-verification session covering professional name, business name, credentials, service area, official contact information, profiles, testimonials, and performance claims.
  2. Create About/author, Contact, Privacy, Terms, medical disclaimer, and editorial/review-policy pages and link them globally.
  3. Correct the telephone URI and replace or remove placeholder social links.
  4. Audit every health, outcome, and corporate statistic. Add primary references or documented first-party methodology; otherwise qualify or remove the claim.
  5. Display linked authorship, semantic publication/review dates, and reviewer information when applicable.
  6. Add truthful BlogPosting and visible-breadcrumb-aligned BreadcrumbList JSON-LD.
  7. Add concise “In brief” or “Key takeaways” sections where useful, followed by evidence, nuance, limitations, and action steps.
Phase 2P1/P2 · 2–4 weeks

Build an intent-led content architecture

  1. Map real Search Console queries, prospect questions, and commercial priorities to one canonical page per distinct intent.
  2. Create verified service pages for functional nutrition, gut health, perimenopause support, functional lab testing, and corporate wellness. Split GI-MAP/DUTCH pages only if each represents a real, distinct service.
  3. Include a direct opening answer, audience, scope and limitations, process, evidence, accurate pricing/timing, FAQs, practitioner identity, and next action on each service page.
  4. Build hub-and-spoke internal links among services, articles, evidence, and the blog hub using descriptive anchors.
  5. Rework the six current articles for intent and evidence quality. Consolidate only genuine overlap; avoid mass-produced question variants.
  6. Add original practitioner assets such as frameworks, decision aids, checklists, consented case methodology, transcripts, or transparent calculators.
Phase 3P2 · 1–2 weeks

Improve experience, crawler access, and distribution

  1. Keep primary pages and article content as server components; isolate only filters, accordions, forms, chat, and sharing into client islands.
  2. Optimize hero/LCP media with responsive Next.js images, explicit sizing, correct priority, and compression. Review the auto-open lead magnet for intrusive-interstitial and conversion impact.
  3. Measure representative templates with field Core Web Vitals and supporting lab diagnostics.
  4. If ChatGPT search visibility is wanted, allow OAI-SearchBot. Decide separately whether to allow GPTBot, which concerns potential training use.
  5. Submit the corrected sitemap to Google Search Console and Bing Webmaster Tools; inspect representative URLs after deployment.
  6. Optionally implement IndexNow for Bing/Copilot freshness. Do not use Google's Indexing API for ordinary pages.

Release gate

Definition of done for the foundational release

  • Preferred public URLs return 200; alternate host/protocol variants redirect once.
  • Every indexable route has unique metadata and one correct self-canonical.
  • /robots.txt and /sitemap.xml return 200.
  • The sitemap contains only canonical, indexable, successful URLs.
  • No page/schema mentions Rosales, lawn care, or unsupported ratings.
  • All metadata and page images return 200 with correct content types.
  • Structured data validates and matches visible, verified information.
  • Navigation contains no placeholder profiles, wrong phone links, or broken links.
  • Health/outcome claims have reviewed evidence, methodology, or qualification.
  • Representative routes pass an automated rendered-metadata smoke test.
  • Representative URLs are inspected in Google and Bing webmaster tools.
  • A search, AI-referral, and business-conversion baseline is recorded.
